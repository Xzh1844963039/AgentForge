## 1. Executive summary

Phase 5 does not add product features for their own sake. It adds a reproducible
evaluation system and uses it to measure the existing Phase 1–4 runtime.

Delivered:

- typed benchmark schema, dataset loader, isolated runtime factory, verifier
  engine, metrics collector, failure analyzer and report generator;
- 34 internal development tasks across all 10 required categories;
- 9 live-acceptance tasks with fixture behavior stripped (Phase 6A added a file task);
- resumable batch execution with JSON/JSONL/CSV/Markdown exports and Git commit
  capture;
- A/B/C ablation (single-agent, multi-agent, multi-agent + memory) with separate
  learning and evaluation tasks;
- explicit live-provider entry point that refuses paid calls without an API key
  and `--allow-live-api`;
- reconciliation state for the previously unprotected execute-vs-audit crash
  window;
- 11 new reliability/fault-injection tests and 6 benchmark tests;
- SQLite index and tool-catalog-cache optimizations with before/after data;
- `agentforge benchmark list|run|compare|report|failures|live`.

**Measured fixture benchmark:** 34 runs, 33 verified passes, 1 needs-review, 0
unexpected failures. **This is a harness/tool/runtime result, not real-LLM
performance.**

The fixture policy is deterministic. The 97.1% result proves that the following

| C — multi + memory | 6/6 | 100.0% | 1.135s | 20,098 | 5 / 0 |

Observations:

- The fixture policy solves the same tasks in all topologies; no completion
  difference is observed.
- Multi-agent uses ~20% more tokens on this subset because synthesis, independent

- n=6, one repeat. No statistical significance is claimed.

The Phase 3 controlled memory experiment remains the only evidence that memory
can change a subsequent tool action; Phase 5 does not pre-write evaluation
answers into memory.

## 7. Fault injection and reconciliation

`tests/test_phase5_reliability.py` contains 11 tests. Together with Phase 4
coverage, the 14 target scenarios are:

1. invalid JSON/action output;
2. tool schema validation failure;
3. repeated action stopped by budget;
4. tool timeout;
5. Docker container killed and restarted;
6. unanswered clarification remains paused;
7. memory retrieval failure is non-fatal;
8. audit-write failure after a side effect enters `NEEDS_RECONCILIATION`;
9. unresolved reconciliation blocks replay;
10. no intent audit means a high-risk tool is not executed;
11. restart after pause resumes persisted workflow;
12. benchmark pause/resume has no duplicate effect;
13. cancellation and delegation-depth safe paths;
14. approval expiry and argument-binding reuse are covered by Phase 4 tests.

Key result: Phase 5 added a durable high-risk intent row before execution. If the
final audit cannot be persisted, the tool result becomes
`NEEDS_RECONCILIATION`, the workflow fails safely, and any later attempt is
refused until a human reconciles the external state. The side effect is not
blindly replayed.

**Exactly-once execution is not claimed.** The platform can prove an outcome is
unknown and fail closed; it cannot prove external side-effect state without
reconciliation.

## 8. Performance optimization evidence

`benchmarks/performance/measure.py` measured the two safe optimizations on 20,000
synthetic tool-call rows and 13 real tool specs.

### SQLite composite indexes

| Query | Before | After | Speedup |
|---|---:|---:|---:|
| `list_tool_calls(workflow_id, task_id)` median | 0.310ms | 0.241ms | **1.29x** |
| `list_tool_calls(task_id)` median | 15.353ms | 0.241ms | **63.8x** |

Before, the task-only query scanned the table; after, it used
`idx_tool_calls_task`. The composite `(workflow_id, task_id, started_at)` index
also replaced the workflow-only index for evidence/replay queries.

### Tool catalog cache

| Variant | Per call | 2,000 calls |
|---|---:|---:|
| Rebuild catalog | 0.1298ms | 259.5ms |
| Cached | 0.000116ms | 0.231ms |
| Speedup | **~1,122x** | |

The cached string is identical; registration invalidates the cache. This is CPU
overhead only, not prompt-token reduction.

### Where time actually goes

- Non-Docker file/approval/planning tasks: ~0.10–0.12s average E2E.
- Python/Docker tasks: ~2.1–2.3s average; the timeout task 4.47s.
- Docker container startup dominates Python-task latency by roughly 2 seconds.
- E2E is therefore dominated by Docker and, for live runs, model latency. The
  benchmark intentionally keeps per-task isolation instead of reusing containers
  across tasks; that would trade correctness/isolation for speed.

Sequential batch execution was retained for comparable measurements. Bounded DAG
concurrency was not enabled in this phase because Docker/CPU contention would
confound before/after timing and requires additional isolation testing.

## 12. Known limitations

1. Fixture results are not real-LLM performance.
2. The dev set has 34 tasks and per-category samples of 3–5; no statistical
   significance claims.
3. Live acceptance, live memory reuse and real-user HITL are NOT VERIFIED.
4. High-risk reconciliation is manual; there is no resolution workflow/UI yet.
5. Low-risk tools do not pre-create reconciliation intents.
6. Cooperative pause/cancel does not preempt an in-flight tool.
7. Docker startup dominates Python-task latency.
8. Batch tasks run sequentially; DAG concurrency is future work.
9. Open-ended research quality still requires human review.
